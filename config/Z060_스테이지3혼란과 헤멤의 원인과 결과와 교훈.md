## 1. 🚨 Stage 3 개발 과정의 근본적 문제 진단

Stage 3(Notion 분석)에서 약 **20시간**의 비효율적인 시간 소모가 발생한 근본 원인은 **'정보의 비대칭성'**과 **'인터페이스 계약 위반'**이었습니다.

### 1.1. 문제의 원인: 쉬운 해답이 보이지 않은 이유

| 문제 영역 | 현상 (서대리/선과장 측) | 나실장처럼 쉬운 대안을 제시 못한 이유 |
| :--- | :--- | :--- |
| **Prio 1: 403 오류** | "새 키 발급" 대신 "코드를 수정"하는 방식으로만 해결 시도. | **행정 권한 부재:** 서대리는 키를 발급할 **행정적 권한(Billing, Console 접근)**이 없어, 코드로만 문제를 해결하려 했음. 나실장은 **키 발급 절차를 안내**하여 행정적 해결책을 제시함. |
| **Prio 2: 400 오류** | **Notion DB 속성명**의 띄어쓰기, 대소문자 등 디테일 불일치. | **물리적 대조 불가:** 코드를 보는 서대리는 **실제 DB 화면(선과장의 영역)**을 볼 수 없어, **'복사-붙여넣기'**라는 가장 쉬운 해결책을 적용하지 못하고 수많은 디버깅을 반복함. |
| **시간 소모** | 서버 미가동 등 물리적 블로커에 시간 소모. | **'실행 환경'**과 **'코드'**를 분리하여 생각하지 못하고, 모든 문제를 코드로만 해결하려 함. |

**핵심 교훈:** **"기술적 난이도가 낮은 문제일수록, 코드가 아닌 '시스템 외부의 환경/인증/권한' 문제일 확률이 높다."**

## 3. 🛡️ 재발 방지 대책 (ZOBIS 거버넌스 강화)

이러한 비효율을 **다시는 반복하지 않기 위해**, ZOBIS 협업 체계에 다음의 **'실행 게이트(Execution Gate)'**를 추가하고 표준화합니다.

### 3.1. [원칙 1] 행정적 블로커 선제적 파악

| 대책 | 내용 | 책임 주체 |
| :--- | :--- | :--- |
| **권한 선점** | 모든 프로젝트 시작 시 **필요한 API 키, DB ID, 공유 목록**을 **나실장/선과장**이 먼저 파악하여 **조대표님께 요청 후 서대리에게 주입**. | 나실장, 선과장 |
| **비용/권한 체크** | 모든 외부 API 사용 전 **결제 활성화 상태** 및 **API Key 제한(Restrictions)**을 서대리가 체크리스트로 검증. | 서대리 |

### 3.2. [원칙 2] 시스템 인터페이스 계약 강화

| 대책 | 내용 | 책임 주체 |
| :--- | :--- | :--- |
| **Fatal 400 Rule** | Notion DB에 데이터 POST 요청 시 **400 Validation Error**가 발생하면, 서대리는 **즉시 디버깅을 중단**하고 다음 3가지 정보를 제출. | 서대리 |
| **Screen vs. Code Check** | 선과장(운영/Notion)은 서대리가 제출한 **실패 JSON**과 **실제 Notion DB 화면 스크린샷**을 **1:1 대조**하여 오류 속성명을 즉시 수정하여 전달. | 선과장, 서대리 |
| **최소 페이로드** | API 연동 성공 전까지는 **'문서 제목, 링크, 상태'** 등 **3~6개 최소 필수 속성**만으로 테스트를 진행하는 것을 강제. | 서대리 |

### 3.3. [원칙 3] 실행 환경 통제

| 대책 | 내용 | 책임 주체 |
| :--- | :--- | :--- |
| **배경 프로세스 관리** | 웹훅 서버 등 배경 실행 프로세스는 **`nohup`** 또는 **`tmux`**를 사용해 **안정적인 실행 환경**을 강제. | 서대리 |
| **터널링 표준화** | `cloudflared` 또는 **배포 환경의 Public URL**만 사용하도록 표준화. | 서대리 |
