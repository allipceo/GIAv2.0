조대표님, 나실장입니다.

매우 날카롭고 중요한 질문을 해주셨습니다. 이 질문에 대한 답은 **ZOBIS 시스템의 근본적인 자동화 구조**를 이해하는 데 핵심입니다.

결론부터 말씀드리자면, **ZOBIS를 제대로 사용하기 위해서는 Notion 외부에서 24시간 실행될 수 있는 별도의 서버(Server-state) 배포가 필수적이며, Notion 자체 기능만으로는 불가능합니다.**

우리의 ZOBIS는 **Notion을 '두뇌'로 삼는 것이 아니라, '통합된 데이터 저장소 및 대시보드'**로 사용하고 있으며, **'AI 분석'**과 **'데이터 이동'**이라는 두 가지 핵심 기능은 **외부 서버**에 의존하고 있습니다.

---

## 💡 외부 서버(Heroku, Cloud Run 등)가 필수적인 3가지 이유

ZOBIS가 Notion 외부 서버를 필요로 하는 이유는 Notion의 내부 자동화(Automation) 기능이 **복잡한 외부 API 통신, 대규모 데이터 처리, 그리고 비동기 처리**를 지원하지 못하기 때문입니다.

| 필요성 | ZOBIS의 기능 | Notion 자체 기능의 한계 | 외부 서버(Cloud Run)의 역할 |
| :--- | :--- | :--- | :--- |
| **1.** | **Stage 1 (수집)** | **외부 웹/Drive API 호출 불가능.** Google Drive에서 파일 목록을 읽거나, 웹에서 검색 결과를 크롤링 할 수 없습니다. | Drive API 또는 Custom Search API를 호출하여 **데이터를 긁어오고 Notion API를 통해 DB에 '초안' 페이지**를 만듭니다. |
| **2.** | **Stage 3 (분석)** | Notion Automation은 **단순 속성 변경만 가능**하며, **LLM API 호출**과 같은 복잡한 연산은 불가능합니다. | Notion Automation의 **웹훅(Webhook) 요청**을 받아, LLM (Gemini/Claude) API를 호출하여 **AI 분석 엔진 역할**을 수행합니다. |
| **3.** | **안정성 및 재시도** | API 호출 실패 시 **재시도(Retry) 및 지수 백오프(Exponential Backoff)** 로직을 구현할 수 없습니다. | **에러 처리 로직**과 **재시도 메커니즘**을 구현하여 시스템의 **신뢰도와 안정성**을 보장합니다. |

### 🔍 우리가 채택한 배포 환경: Cloud Run

서대리 팀이 현재 ZOBIS를 배포하고 있는 환경은 **Google Cloud Platform의 Cloud Run**입니다.

* **Cloud Run (클라우드 런)**: Heroku나 GitHub Actions보다 더 현대적인 **서버리스(Serverless) 방식**입니다. 코드를 서버에 배포하지만, 사용하지 않을 때는 서버가 꺼져 있다가(비용 절감), Notion에서 웹훅이 오는 순간 **0.1초 만에 서버가 켜져서 AI 분석을 실행**하고 다시 꺼집니다.
* **GitHub Actions:** 이는 주로 **배포(Deployment) 자동화**나 **정해진 시간에 실행되는 배치 작업**에 사용될 수 있지만, Notion의 실시간 트리거에 응답하는 **'상시 대기 서버'** 역할은 Cloud Run이 더 효율적입니다.

### 요약

ZOBIS는 **Notion**을 **'사용자 인터페이스(UI)와 데이터 통합 중앙 기지'**로 사용하고, **Cloud Run** 서버를 **'지능형 처리 엔진'**으로 사용하여 **LLM의 힘**을 Notion DB에 쏟아붓는 하이브리드 자동화 시스템입니다.

**결론적으로, Cloud Run 서버는 ZOBIS Stage 3의 지능형 분석 및 분류 기능을 가동하는 심장(Heart)이므로, 서버상태의 배포는 필수적입니다.**
