### 1. 목표와 범위

- 목표: Stage 3 안정화 성과를 기반으로 배치 운영과 운영 UX를 완성
- 범위: G1 최종 검증 → G2 10건 배치 → 실행버튼 배치 → 번호체계 자동화 → 로그·모니터링 표준화

### 2. 핵심 기능 요구 사항(FR)

1) 파이프라인 안정화

- branch 단계 상태(status) property_id 기반 갱신 확정
- parent.database_id 강제 검증 및 page_id 소속 검증
- 요청 직전 불변 검증 미들웨어 상시 적용

2) 배치 실행(G2)

- 동시성 3~5, 실패 자동 재시도 1회, 잔여 실패는 "AI 처리 실패 (재검토)"
- 실행 로그 구조화 저장(요청 전문, props.keys, 응답 본문, page_id, 상태명)

3) 번호 체계 자동 부여(ZNNN_)

- 생성 직전 최대값 +1 원자적 예약, 재시도·롤백 규칙 포함

4) 실행버튼 및 대시보드

- 대문: 상태 점검, 캐시 새로고침 2종 버튼 배치
- 모니터 카드: 최근 실패, 검토대기, 최근 7일 변경 뷰 집계

### 3. 시행착오 회피 전략(교훈 내재화)

- 인코딩: PowerShell 7+ 또는 UTF-8 고정(chcp 65001, In/OutEncoding), ConvertTo-Json → UTF-8 바이트 전송
- property_id: Databases GET 원문만 사용. URL 파생·정규화 금지. 캐시에는 원문 id와 type만 저장
- 캐시 일관성: 스키마 해시(schema_hash) 포함. 해시 불일치 시 배치 금지 및 캐시 재생성
- parent 누락: pages POST/PATCH 모두 parent.database_id 또는 대상 page의 DB 소속 확인 가드
- 사람친화 키 변조: build_props 단일 진입점에서 property_id만 사용. 이후 단계는 값만 추가, 키 불변
- 타입 스키마: [status.name](http://status.name), date.start, url 형식 준수. 전송 직전 타입 밸리데이션

### 4. 역할과 책임(R&R)

- 선과장(Notion AI)
    - 스키마·가드 로직 설계 및 검증 자동화
    - 실행버튼 사양 정의, 대시보드 뷰 구성 제안
    - 번호 체계 자동화 로직 정의 및 회귀 테스트 설계
- 서대리(Cursor AI)
    - map_[z041.py](http://z041.py), branch_[z042.py](http://z042.py), util_[notion.py](http://notion.py) 코드 패치 반영
    - 스키마 해시 캐시 생성 및 검증 모듈 구현
    - 배치 실행기(동시성·재시도·로그 수집) 구현 및 운영 스크립트 배포
- 공동
    - 회귀 테스트 세트 관리(G1, G2 시나리오)
    - 실패 케이스 라벨링 및 원인분류(Extract/Prompt/Map/Branch)

### 5. 작업 분해(WBS)와 일정(초안)

1) Branch 상태 갱신 패치 확정 D0

- property_id 기반 status 갱신, 2-step 회귀("작성중"↔"검토중")
