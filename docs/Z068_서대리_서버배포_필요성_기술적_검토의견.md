- 규범·체계 운영: 임계값 정책·속성 매핑·운영 규범 문서화와 대시보드 구성은 Notion 내부에서 충분합니다.[[4]](https://www.notion.so/Z059_Stage-3-V1-0-aee610dbcf7b418f82aef1e26a3c5204?pvs=21)[[5]](https://www.notion.so/Z042_-V1-0-49ee29786d524f54b7fbf4b777064760?pvs=21)[[6]](https://www.notion.so/Z068_Stage-3-3561ce127e2e4484adf2b676f9479707?pvs=21)

외부 런타임이 꼭 필요한 이유와 범위

- 웹 수집과 API 호출(Stage 1): 웹 검색, 크롤링, 인증 키 관리, 쿼터·403/429 대응, 재시도·서킷브레이커는 Notion 내부에서 수행할 수 없습니다. 전용 어댑터와 런타임이 필요합니다.[[7]](https://www.notion.so/Z068_Stage-3-3561ce127e2e4484adf2b676f9479707?pvs=21)
- 파일 이동·전처리(Stage 2): Drive 저장, 포맷 변환, 오류 복구, 배치·스케줄 실행은 외부가 안정적입니다.
- 트리거·큐·로그: 웹훅 수신, 실패 큐, 지표(P50/P95) 집계, 키 마스킹 로그 등 운영 인프라는 서버/서버리스 쪽이 안전합니다.
- 대체 공급자 스위치: CSE 장애 시 Bing/SerpAPI로 즉시 전환하는 어댑터 아키텍처는 외부에서 관리해야 합니다.

- 필수 최소(현재 우리가 운영 중)

    - 외부 런타임: A2G2N 파이프라인의 수집·이관·트리거, 키/권한 관리, 재시도·로그[[8]](^https://www.notion.so/3561ce127e2e4484adf2b676f9479707)
